## 一、结论摘要

方案的分层（L0–L4）、契约先行、"每步可停"的迁移节奏是站得住的；第 2 轮自评审抓出的 5 个问题（numpy 依赖口径、双臂编排无家、`WaistPolicy` 漏注册、线程/状态污染无契约、ACM 随机性）都是真问题，方向正确。

不通过项集中在三类：

1. **契约层不完整**（B8）：`GroupPlan`/`PlanMeta` 只被引用未定义，缺过渡产物、缺坐标系/单位/姿态表示、缺读写与版本协商 → 现在冻结等于把返工留到步 4。
2. **配置层不成立**（B2/B3）：`description` 缺 kinematics/contact-manager 两个 yaml；URDF/SRDF 内是写死的绝对 `file://` 路径，`mesh_root` 机制在当前描述文件上无法生效；左臂标定并非 `derive: mirror`。
3. **管线描述与实现相反**（B1）：方案把 `densify_and_scan` 画在 `solve` 之后，实际是"先加密航点再 IK 求解"，且规划链路的碰撞校验主力来自 Descartes 内部边校验，不是库后置扫描。

## 三、必须修订项

### B1（高）§6.1 管线顺序与实现相反，碰撞校验归属说错

**证据**：实际流程是"笛卡尔航点加密 → IK 采样(Descartes) → TOTG → 精度/副指验证"，加密发生在求解**之前**：

```459:462:circle_planning_7axis.py
    # 航点已足够密，阈值设成略大于间距即可避免插值产生新的、可能无解的位姿
    spacing = 2.0 * math.pi * SIZE / N_POINTS
    interp = generateInterpolatedProgram(program, robot.env, 0.1, spacing * 1.05, 0.1, 1)
```

碰撞校验实际分两类：① **规划器内部状态/边校验**（依赖 ACM + collision margin，所以 `fix_allowed_collisions` 不做则"任何位形都报几十个碰撞，规划必然失败"）；② 库的**显式后置扫描**只用于过渡轨迹、双臂互碰、副指随动（`522:538`、`665:697`）。

**影响**：按方案实现会（a）把加密放到求解后，与演示行为不等价；（b）在单臂形状链路上重复加一次全量扫描，等于改变 golden 基线（部分形状可能由 PASS 变 FAIL）。

**建议**：§6.1 改为 `interpolate(targets) → solve_cartesian(IK) → time_parameterize → verify`，并把碰撞校验拆成"规划器内部边校验（必经）"与"库后置显式扫描（过渡/双臂/副指）"两类分别落位。

### B2（高）§4.2 `description` 缺件，`mesh_root` 机制在当前描述文件上不成立

**证据**：SRDF 内引用另外两个绝对路径 yaml：

```94:97:tienkung_dex/urdf/tienkung_dex.srdf
    <kinematics_plugin_config filename="file:///home/qingxiangliu/work/dex_planning/tienkung_dex/urdf/tienkung_dex_plugins.yaml" />
    <contact_managers_plugin_config filename="file:///home/qingxiangliu/work/dex_planning/tienkung_dex/urdf/contact_manager_plugins.yaml" />
```

URDF 的 mesh 同样全部是绝对 `file://` 路径，且含中文文件名（如 `腕部相机右.STL`）。此外 demo 里的 `URDF`/`SRDF` 常量本身也是写死的本机绝对路径：

```83:84:circle_planning_7axis.py
URDF = "/home/qingxiangliu/work/dex_planning/tienkung_dex/urdf/tienkung_dex.hand.urdf"
SRDF = "/home/qingxiangliu/work/dex_planning/tienkung_dex/urdf/tienkung_dex.srdf"
```

**影响**：① `description` 必须是 **urdf + srdf + kinematics_plugin yaml + contact_manager yaml** 四件套，方案只写了 urdf/srdf/mesh_root；② 库必须实现"加载前重写描述文件内 `file://` 前缀"，`mesh_root` 才可能有作用——该动作在方案中完全缺失，而它是 P-C"换 YAML 即用"与换机部署的前提；③ 中文文件名 + 未做 URL 编码的路径应进入跨平台风险表。

**建议**：§4.2 `description` 扩为四键，新增"路径重写/解析规则"小节（重写发生在 `Robot.from_files` 之前，重写后的临时描述文件的生命周期与缓存策略需写明）；§10 风险表补"描述文件绝对路径与中文文件名"一行。

### B3（中）§4.2 `calibration.left: {derive: mirror}` 表述与实现不符

**证据**：左臂不是由右臂做数学镜像求值，而是**逐位符号枚举 2^7 + 限位过滤 + FK 残差择优**，且 URDF 左右不严格对称（实测残差 ~1mm / 0.003rad，故阈值放宽到 5mm/5mrad，`271:275:circle_planning_7axis.py`）。

**影响**：`derive: mirror` 会让实现者以为是一个纯变换，进而把标定简化成 `MIRROR_SEED`。

**建议**：配置改为 `left: {calibrate: mirror_sign_enum, target: mirror(right)}`，并把"残差超阈告警/失败即拒启动"写成加载校验项。

### B4（中）§8.3 对 ACM 不确定性的诊断偏了

**证据**：随机性其实已被 `np.random.default_rng(0)` 钉住（`373:373:circle_planning_7axis.py`）。真正的不确定性是**配置相关**：采样分布随模式不同（`sample_full`/`sample_fixed`/`sample_w`，`748:791`），且 `pairs()` 遍历的 `cfgs` 条目数随 `--arm` 变化（`363:371`）→ 单臂/双臂、各模式发现的"结构性重叠"对集合本就不同。

**影响**：只按 profile 缓存一份 `collide_cache.yaml` 会掩盖"不同配置得到不同 ACM"的事实，基线不可复现。

**建议**：缓存键至少为 `(profile, 采样规格)`，或"一次算全集、所有模式共用"；无论哪种，都必须在 golden 基线中记录 ACM 内容 hash，并确认该口径不改变现有 19 组合的通过状态。

### B5（中）§5 状态不外溢契约与现有实现存在两处真实依赖，需划边界

**证据 1**：`main` 一次性写入 `other_pos` 后，依赖"此后任何 setState 都不碰这些关节"：

```1267:1272:circle_planning_7axis.py
    # 把显示/固定的手部姿态写入环境：之后的 ACM 采样与规划碰撞检查都能看到
    # 真实的手部状态（其余手指的值此后不再被任何 setState 改动，保持不变）
    for side in SIDES:
        op = cfgs[side].get("other_pos", {})
        if op:
            robot.env.setState(list(op), np.array([op[n] for n in op], float))
```

**证据 2**：`waist free + both` 的冻腰注入是**跨调用存活的会话状态**（`set_frozen_waist` 单元格 + 左臂后续调用读取）：

```827:830:circle_planning_7axis.py
            if not waist_owned:              # both 模式左臂：右臂规划后注入冻结腰值
                def set_frozen(w, cell=frozen_waist):
                    cell["w"] = np.asarray(w, float)
                cfg["set_frozen_waist"] = set_frozen
```

**建议**：① 契约写死"快照包含全关节值（含 `other_pos` 涉及的关节），恢复即还原"；② 冻腰这类跨调用状态显式标注为"编排器持有的会话状态"，不要靠 env 恢复兜住；③ 明确快照范围是**仅关节值**还是也含 ACM / margin / active links（这三者同样是 env 全局态）。

### B6（中）§7 `TimeParamApi` 入参在"纯 numpy 出参"约束下不自洽

**证据**：TOTG 的输入是 tesseract 程序对象 + URDF 速度限位：

```499:519:circle_planning_7axis.py
    from tesseract_robotics.tesseract_time_parameterization import (
        TimeOptimalTrajectoryGeneration)
```

**影响**：若门面入参是 L0 `JointTrajectory`，库内必须重建 state waypoint program，且**没有 URDF 速度限位时该能力不可用**；重建结果与离线规划器内嵌 TOTG 结果是否一致也需表态。

**建议**：在 §5/§7 写明 `TimeParamApi(Q, joint_names, profile)` 的入参形态、内部重建步骤、"无 URDF 不可用"的边界，以及回退链（TOTG → uniform）的触发条件（现实现为异常或返回值双重判定）。

### B7（中）§6.3 `ModeStrategy` 协议漏掉模式差异的真正载体

**证据**：三模式差异不止 `group/variables/ik/target_pose/hand_joints`，还包括：`sample_state`（决定 ACM 采样，进而影响 B4）、`seed_plan`、`plan_rotation`/`tip_offset`（fixed 的换算基准）、`other_pos`（显示与碰撞可见性）。见 `793:939:circle_planning_7axis.py`。

**建议**：把扩展点改为"**策略产出结构化 `ModeConfig` dataclass**"，而非"策略=一组方法"；这样 §8.1 的步 2（cfg dict → dataclass）与步 3（if/elif → 注册表）可合并为一次改动，风险更低。

### B8（高）§4.1 契约草案引用未定义类型，且缺关键信息

**问题清单**：

1. `GroupPlan`、`PlanMeta` 被引用但未定义。
2. `waypoints: np.ndarray | None` 未承载 per-group 语义（`both` 模式下右侧为基准、左侧镜像）；每组还需要 tip_frame、理想路径、误差、副指 delta、冻结腰值。
3. `@dataclass(frozen=True)` 内含 `np.ndarray`：仅禁止属性重绑定，数组仍可被就地改写，且实例不可 hash（不可用于缓存键）。
4. `positions` 与"关节名字典 `{joint_name: rad}`"两套表示并存，序列化格式未定唯一表示。
5. 缺**过渡轨迹产物**，而 §7 的 `plan_transition(plan_a, plan_b)` 需要它；随机路标回退还需要参数空间 limits，故 artifact 必须能唯一定位 profile（建议 `profile_id + hash`）。
6. 缺契约**读写 API** 与**版本协商**（`load_artifact()` 如何拒绝过新的 `schema_version`）。
7. 缺系统性 **坐标系/单位/姿态表示/时间基准**声明：现实现全部为 pelvis 系 + 米/弧度；姿态在 URDF/产物侧是旋转矩阵、在 RViz 侧是四元数；时间在 TOTG 下是 `time_from_start`。这三条是 P-A→P-B 对接最易踩的坑。

**建议**：冻结 L0 前补齐上述 7 项，并配套"序列化往返测试 + 版本拒绝测试"（对应 §8.3 单元测试清单）。

## 四、迁移步骤风险（§8.1）

### C1（高）漏了"步 0.5：消除 import 副作用"，它是步 2/步 4 的硬前置

**证据**：模块级执行 `argparse`、绝对路径常量、全局 `SIDES/SHAPES/FINGER/IK_*`：

```193:214:circle_planning_7axis.py

MODE = ARGS.mode
FINGER_NAME = ARGS.finger_joint
```

回归脚本正依赖这个副作用（先改 `sys.argv` 再 import）：

```13:21:tests/regression.py

waist = sys.argv[3] if len(sys.argv) > 3 else "fixed"
fingers = sys.argv[4] if len(sys.argv) > 4 else None

    _argv += ["--fingers", fingers]
```

**影响**：只要 L2 的 `RobotProfile`/`PlannerOptions` 落地，这层必须拆；拆掉会同时改变测试的进入方式。它不属于"纯机械搬家"，方案步 0–步 5 未覆盖。

**建议**：单列步 0.5「消除 import 副作用（配置注入 + 路径外部化 + 测试改为真 API 调用）」，并标注其依赖步 0 的 golden 基线。

### C2（中）步 1「纯机械搬家 / 半天」低估

**依据**：tesseract 调用遍布全文件（手写 DLS IK、Descartes `DescartesMoveProfileD` trampoline 子类、ACM、ContactManager、TOTG），方案自身也列了三条"已知陷阱"注释（`383:401:circle_planning_7axis.py`）。建议步 1 工作量按 1–2 天评估，且必须在步 0 完成后开始。

### C3（中）基线阈值口径不一致

**证据**：README 宣称"主指尖路径误差 ≤0.01mm"，回归判据是 0.1mm：

```90:92:tests/regression.py

            print(f"FAIL {shape} {side}: 路径误差 {perr:.4f}mm 离面 {dev:.4f}mm")
            ok = False
```

**建议**：步 0 固化基线时统一并记录"判据阈值 + 实测值 + 关节裕度 + 单形状耗时 + TOTG 是否产出时间戳"，作为 golden 基线文件的一部分。
